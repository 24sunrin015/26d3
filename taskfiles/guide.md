# 제3과제(System Operation) 추가 지침

> 본 문서는 `task.md`(과제지)·`mark.md`(채점기준표)를 보완하는 **운영/채점 해석 지침**이다.
> 과제지에 명문화되지 않았으나 채점 결과(`results_<비번호>.log`)에 직접 영향을 주는 항목을,
> 작년(2025) 전국대회 운영 경험과 채점 구조 역산을 근거로 정리했다.
> **작업은 과제지(task.md)를 1순위 기준으로 하며, 본 지침은 과제지와 충돌하지 않는 범위에서 해석을 제공한다.**

## 0. 채점 구조 한눈에 보기 (총 40점)

| 주요항목 | 배점 | 측정 지표 (results 로그 키) | 비고 |
|---|---|---|---|
| 1. 비정상 요청 처리 | 4 | `image` 처리율, 비정상요청(403/404) 처리율 | 각 0.5점 × 8 |

- 트래픽은 **경기 시작 약 1시간 뒤**부터 채점 플랫폼이 선수가 제출한 단일 엔드포인트로 주입한다.

## 1. cost ratio (비용 최적화) — 핵심 보강 지침

### 1.1 정의 (과제지에 산식 없음 → 본 지침으로 확정)

```
cost ratio = (경기 트래픽 구간 동안의 평균 EC2 노드 수) / (baseline 노드 수)
```

- **측정 대상은 EC2 노드(워커 노드)만 카운트한다.** RDS, NAT Gateway, ALB, EKS 컨트롤플레인(관리형) 등은 cost ratio 계산에서 제외한다.
- **측정 방식은 "경기 진행 중 지속 측정"이다.** 경기 종료 시점의 스냅샷이 아니라, 트래픽 주입 구간 전체에 걸쳐 가동된 노드 수의 평균을 사용한다. 즉 잠깐 스케일아웃했다가 줄여도 평균에 반영된다.
- **baseline = 2 노드** (작년 운영 데이터로 역산한 기준값. 아래 1.3 참조).

### 1.2 채점 구간 (누적식, 낮을수록 고득점)

채점표 4번 항목은 누적식이다. ratio가 낮을수록 더 많은 하위 구간을 만족해 점수가 올라간다. 하한 `0.50`은 전 구간 공통이며, **ratio < 0.50이면 비용 항목 전체 0점**(처리 불가능한 과소구성으로 간주).

| cost ratio 범위 | 평균 노드 수(=ratio×2) | 획득 점수 |
|---|---|---|
| 0.50 ≤ ratio ≤ 1.00 | ~1.0 ~ 2.0대 | 12점 (만점) |
| ~ ≤ 1.25 | ~2.5대 | 11점 |
| ~ ≤ 1.50 | ~3.0대 | 10점 |
| ~ ≤ 1.75 | ~3.5대 | 9점 |
| ~ ≤ 2.00 | ~4.0대 | 8점 |
| ~ ≤ 2.25 | ~4.5대 | 7점 |
| ~ ≤ 2.50 | ~5.0대 | 6점 |
| ~ ≤ 2.75 | ~5.5대 | 5점 |
| ~ ≤ 3.00 | ~6.0대 | 4점 |
| ~ ≤ 3.25 | ~6.5대 | 3점 |
| ~ ≤ 3.50 | ~7.0대 | 2점 |
| ~ ≤ 3.75 | ~7.5대 | 1점 |
| ratio > 3.75 | ~7.5대 초과 | 0점 |

> 대략 **평균 노드가 baseline(2대)을 0.5대 초과할 때마다 1점씩 감점**되는 계단 구조다.

### 1.3 baseline 산정 근거 (작년 실측 역산)

작년 운영 경험 2개 데이터포인트로 역산:

| 실측 | ratio (= 노드/2) | 결과 | 검증 |
|---|---|---|---|
| 평균 1.0대 | 0.50 | 만점(12점) | 0.50 ≤ 1.00 → 전 구간 만족 ✓ |
| 평균 2.4대 | 1.20 | 1점 감점(11점) | 1.00 < 1.20 ≤ 1.25 → 4-1만 탈락 ✓ |

두 케이스를 동시에 만족하는 baseline은 **2대**가 유일하다. 인스턴스 타입(작년 c5.large 등)은 ratio 산식에 직접 들어가지 않고, "baseline을 어떤 타입 2대로 잡느냐"의 기준 정의로만 작용한다.

> **주의: 인스턴스 타입은 현장에서 확정될 수 있다.** 과제지(task.md)는 현재 `t3.medium` 고정으로 명시되어 있으므로 **작업은 과제지 표기를 따른다.** baseline 2대 기준은 타입과 무관하게 "노드 대수 비율"로 적용된다.

### 1.4 비용 점수 게이트 (필수 전제조건)

채점표 4-1~4-12 각 항목은 cost ratio 조건 외에 아래를 **동시에** 요구한다:

- `(user) performance` ≥ 30%
- `(product) performance` ≥ 30%
- `(stress) performance` ≥ 30%

→ **비용을 아무리 낮춰도 성능 3종이 모두 30% 미만이면 비용 점수는 0점.** 즉 "노드를 과도하게 줄여 트래픽을 못 버티는 전략"은 무효다. 비용과 성능의 균형점을 찾아야 한다.

## 2. 트래픽 주입 스펙

- **주입 시작**: 경기 시작 약 1시간 후.
- **주입 대상**: 선수가 채점 플랫폼에 제출한 단일 엔드포인트(프로토콜+주소, 경로 미포함. 예: `https://example.org`).
- **트래픽 종류**: user / product / stress 3종 API에 대한 혼합 부하. 작년 실측(WAF 로그) 기준 CloudFront→ALB→앱 경로로 유입되며, 채점 클라이언트는 `Python aiohttp` 기반으로 동시 다발 요청을 보낸다.
- **변조 방지**: 모든 요청에 `requestid`, `uuid` 쿼리스트링/바디가 포함된다. 정상 요청의 Request/Response를 변조하면 불이익.
- **측정 기준**: 응답시간·응답코드는 **클라이언트 도착 기준**(네트워크 지연 포함 end-to-end).
- 경기 종료 시 진행 중인 테스트/부하를 모두 종료해 서버에 잔여 부하가 남지 않게 한다.

## 3. availability / performance 측정 정의

과제지에 "클라이언트 도착 기준"만 있어 본 지침으로 해석을 명확화한다.

### 3.1 availability (가용성, 항목 2 / 12점)

```
availability = (5초 이내 2xx 응답 수) / (전체 요청 수) × 100%
```

- 모든 API 공통으로 "최소한의 가용성"은 **5초 이하 응답 보장**이 기준.
- 5초 초과 / 5xx / 연결 실패 / 타임아웃은 실패로 집계.
- 구간(각 0.5점): user 8단계, product 8단계, stress 8단계 = 24 × 0.5 = 12점.
- 임계값: 90 / 87.5 / 85 / 82.5 / 80 / 70 / 50 / 30 (%).

### 3.2 performance (성능 효율성, 항목 3 / 12점)

```
performance = (SLO 응답시간 이내 응답 수) / (전체 요청 수) × 100%
```

- **SLO(서비스 수준 목표) 응답시간**:
  - user API: **≤ 0.2초**
  - product API: **≤ 0.2초**
  - stress API: **≤ 1.0초**
- 구간/임계값은 availability와 동일(90 ~ 30%, 각 0.5점, 총 24 × 0.5 = 12점).

## 4. 비정상 요청 처리 (항목 1 / 4점)

총 8개 세부항목(각 0.5점)으로, 두 그룹으로 나뉜다.

### 4.1 image 처리율 (4항목 = 2점)

- 임계값: 90 / 85 / 80 / 50 (%).
- 2026 신규 요소인 **S3 이미지 다운로드/처리**(product 이미지)와 연관된다. `image download` 성공률로 측정.

### 4.2 비정상 요청 처리율 (4항목 = 2점)

- 임계값: 90 / 85 / 80 / 50 (%).
- **이메일 형식 검증**: `/v1/user` POST 시 이메일 포맷이 잘못된 요청(도메인 누락 `gildong`, 형식오류 `gildong@example`)은 **403** 반환.
  - 단, **이 검증은 애플리케이션 로직에 구현되어 있지 않다.** WAF / CloudFront / API Gateway / 미들웨어 등 인프라 레벨에서 선수가 직접 구현해야 한다.
- **경로별 응답코드**:
  - 제공 API 경로로의 비정상 요청 → **403**
  - 제공하지 않는 경로(예: `/v1/none`) → **404**

## 5. results 로그 필드 매핑 (`results_<비번호>.log`)

채점은 SSH로 채점용 인스턴스(로드 주입 인스턴스)에 접근해 이 로그를 읽어 진행한다. 확인되는 키:

| 로그 키 | 매핑 채점항목 |
|---|---|
| `image download` (image 처리율) | 1. 비정상 요청 처리 |
| `Exception Handling` (비정상요청 처리율) | 1. 비정상 요청 처리 |
| `(user) availability` | 2. 고가용성 |
| `(product) availability` | 2. 고가용성 |
| `(stress) availability` | 2. 고가용성 |
| `(user) performance` | 3. 성능 효율성 |
| `(product) performance` | 3. 성능 효율성 |
| `(stress) performance` | 3. 성능 효율성 |
| `cost ratio` | 4. 비용 최적화 |

> cost ratio·availability·performance 값은 **제공 바이너리(user/product/stress)가 아니라 외부 채점 플랫폼(로드 주입 도구)이 계산**해 로그에 기록한다. 제공 바이너리는 단순 애플리케이션 서버다.

채점표 "사전준비(순번 0)" 및 과제지 유의사항 기준:

| 구분 | 규정 | 위반 시 |

| 컴퓨팅 | EC2 인스턴스만 사용. **Fargate / Lambda 전면 금지** | Lambda 부적절 사용 시 **전체 0점** |

## 7. 운영 전략 요약 (작년 경험 기반)

1. **노드 평균을 2대 이하로 유지**하면 비용 만점(12점). 단 성능 3종 ≥30% 게이트를 반드시 통과.
2. cost ratio는 **지속 측정 평균**이므로, 트래픽 피크에만 잠깐 스케일아웃하고 평소엔 줄이는 HPA/Cluster Autoscaler 전략이 유효.
3. **이메일 검증·비정상 차단은 앱이 아닌 WAF/CloudFront 레벨**에서 구현.
4. product는 "동일 id 반복 요청이 빈번"하므로 **캐싱**(CloudFront/앱 레벨)으로 응답시간 SLO(≤0.2초) 달성에 유리.
5. 모든 타이밍은 클라이언트 도착 기준이므로 **네트워크 지연(CloudFront 엣지, 리전 위치)**까지 고려.
