# disassembly — Go 바이너리 로직 추출 툴

현장에서 지급되는 Go 앱 바이너리(user/product/stress)를 사람이 읽을 수 있는 형태로 풀어낸다.
어떤 요청을 어떤 조건으로 비정상 처리하는지, 응답을 어떻게 다르게 내리는지를 코드 레벨에서 파악하는 게 목적이다.

## 왜 필요한가

과거 대회 바이너리는 코드 안에서 특정 데이터를 근거로 응답을 조금씩 다르게 내려 비정상 요청 여부를 갈음하고,
그걸 막았는지까지 클라이언트에 되돌려준 적이 있다. 이런 로직은 과제지에 안 적혀 있으니 바이너리를 직접 뜯어봐야 한다.

## 한계부터 짚고 간다

Go 바이너리는 진짜 `.go` 원본으로 되돌릴 수 없다. 컴파일 과정에서 구조가 사라지기 때문이다.
그래서 이 툴은 원본 복원이 아니라 **읽을 수 있는 재료를 뽑는 데까지**만 한다. 세 단계로 보면:

1. 재료 추출 — 함수명·타입·문자열·파일:줄. `go tool`과 `strings`가 한다. AI 아님.
2. pseudocode — 어셈블리를 C 유사 코드로. Ghidra 디컴파일러가 한다. 이것도 AI 아니고 결정론적 알고리즘이다.
3. `.go` 재구성 — 위 재료를 AI에 먹여 복원. 이 단계는 툴 밖이다.

경기장에서는 AWS Q Developer만 쓸 수 있으니, 툴이 1·2단계 재료를 뽑아두면 그걸 Q Developer에 붙여넣어 3단계를 돌린다.

## 사용법

```bash
./disasm <바이너리> [--all]
```

예:

```bash
./disasm ../../provided/user
```

결과는 `./disassembly/<바이너리명>-<YYYYMMDDHHMMSS>/`에 쌓인다.
기본은 앱 함수(`main.*`, 모듈 패키지)만 디컴파일한다. `--all`을 붙이면 전체 함수를 푼다(느리다).

## 나오는 것들

| 파일 | 내용 |
|---|---|
| `REPORT.md` | 요약: 감지 tier, 파일 목록, 다음 단계 |
| `00_buildinfo.txt` | Go 버전, 의존성, 빌드 플래그 |
| `01_symbols.txt` | 앱 함수 목록 (핸들러가 어디 있는지) |
| `02_strings.txt` | 라우트, SQL 쿼리, 환경변수 키 |
| `03_funcmap.tsv` | 함수 → 파일:줄 → 주소 |
| `04_objdump_src/` | 앱 함수별 소스 주석 디스어셈블리 |
| `pseudocode/` | Ghidra C 유사 pseudocode (함수당 한 파일) |

로직 재구성에는 `pseudocode/`와 `04_objdump_src/`가 핵심이고, `02_strings.txt`가 응답·쿼리 단서를 보탠다.

## 3단계 tier

바이너리 상태에 따라 뽑히는 양이 달라진다. 툴이 자동으로 감지해 `REPORT.md`에 적는다.

- A — 심볼도 있고 소스도 이 머신에 있는 경우. `objdump -S`가 실제 Go 소스 줄까지 붙여준다. 훈련 때 자기 빌드를 뜯을 때 여기 해당한다.
- B — 심볼은 있는데 소스가 없는 경우. 현장에서 지급 바이너리를 받으면 대개 이쪽이다. 함수명·타입·pseudocode는 다 나온다.
- C — stripped 바이너리. DWARF가 없어도 Ghidra의 Go 분석기가 함수명과 타입을 상당 부분 복구한다. 문자열과 pseudocode도 그대로 나온다.

## 요구 환경

- Docker — Ghidra를 `blacktop/ghidra` 이미지로 돌린다. amd64/arm64 멀티아치라 맥(훈련)이든 EC2(현장)든 같은 명령으로 동작한다.
- go — 재료 추출 계층에 쓴다. 없으면 이 계층은 건너뛰고 `strings`만으로 진행한다.

첫 실행 때 이미지를 받느라 시간이 걸린다(약 730MB). 이후로는 캐시를 쓴다.
바이너리 하나 분석에 3분 안팎 걸린다.

## 현장 순서

1. 임시 EC2에 이 폴더째 올리고 Docker·go를 준비한다.
2. `./disasm <지급바이너리>`로 재료를 뽑는다.
3. `pseudocode/`의 핸들러 파일과 `02_strings.txt`, `04_objdump_src/`를 Q Developer에 붙여넣어 로직을 해석하거나 `.go`로 재구성한다.
4. 파악한 검증·응답 규칙을 WAF·앱 대응에 반영한다.

## 구성

- `disasm` — 전체 흐름을 엮는 셸 스크립트
- `ghidra_scripts/DecompileDump.java` — Ghidra headless가 호출하는 디컴파일 덤프 스크립트
- `disassembly/` — 실행 결과 (git에 안 올린다)
